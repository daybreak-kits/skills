# Coding

## 目标与授权

产出是**一个能被信任地合并的 diff**：它解决的正是被要求解决的问题，改动小到能一眼看懂，验证过程别人能重放。不是"写了多少"，也不是"结构多漂亮"。

**你被授权做的事**（默认直接做）：

- **实现路径自己定**：算法、命名、文件内的组织方式，全由你判断。
- **能查清的事自己查，不要问**：现有实现、调用方、项目惯例、报错原因——用只读手段能拿到的答案，不许推回给用户。
- **有更好的方案就说**：发现需求有更简单的解法、或与现状矛盾，直接讲并给出你的倾向，不必先求许可。
- **可以偏离下面的启发式**：只要有更好的理由，在汇报里说明理由即可，不需要请示。

**先说明、再动手**（说明的是理由，不是请求许可）：新增文件或第三方依赖、改动函数签名、跨出任务范围的重构、schema / migration 变更。

**停下来问**：不可逆或高代价的动作（force push、删分支、`rm -rf`、删数据、改生产）；确实查不到的信息；纯偏好无从推断的选择。

## 先复现，再定位，后修改

修 bug 时这三步是硬顺序，跳过任何一步都在赌：

1. **复现** — 拿到失败证据：报错原文、错误输出、失败断言。没有失败证据，就不算定位到问题。
2. **确认在执行路径上** — 改之前确认要改的代码真的在跑。不确定就在该处加日志或故意抛错，跑一次复现步骤。
3. **现象没变 = 改错了地方** — 改完毫无变化，第一怀疑对象是"改了不被执行的副本"（另一份实现、缓存、未重载的模块），而不是"改得不够多"。回代码路径验证，别叠加改动。

## 红线（五条）

1. **禁止平行实现** — 同一逻辑只允许一份实现。不造 `xxx_v2` / `xxx_new` / `xxx_copy`；要替换就原地改，或提出"新实现 + 删除旧实现"的完整方案。发现已有两份，停下报告位置和差异，问清哪份权威——不自选一份改，更不造第三份。
2. **秘密不落盘** — 密码、密钥、token 不进代码、配置样例或任何会进版本控制的文件。
3. **不可逆操作先确认** — 见上节。
4. **不静默吞错** — 内部纯逻辑不加 try/except；错误处理只放在真正的外部边界（网络、IO、子进程、跨服务、用户输入）。边界处校验输入，不信任外部数据。
5. **改签名先列调用方** — 改函数签名或改变语义前，用结构工具列出全部调用方，逐个确认已同步。

## 工作循环

1. **侦察**（义务，不是建议） — 三件事：找现有实现（带同义词搜：fetch/get/load、check/validate/verify；翻 utils/lib/common）；找唯一事实源（这段逻辑只有一处实现吗，调用方从哪 import）；找周围惯例（错误处理、命名、测试怎么写）。
   *完成标准：说得出"这段逻辑现在住哪、谁在调它"，并写下这次改动的成功标准——跑什么、看到什么算过。后面第 4 步按它判定。*
2. **说出理解** — 一两句话讲清要做什么、关键假设是什么。有困惑在这里暴露，别带着疑惑跑一路。
3. **实施** — 多步任务先列清单并随进度更新；每个关键节点对照最初目标核一次，防长链漂移。
   *完成标准：diff 里每一行都能回答"为什么需要它"。*
4. **验证** — 先跑与改动最相关的窄测试，再放大范围，遵循项目自己的命令。
   *完成标准：能跑 + 成功标准全部满足 + diff 干净（无计划外新文件、无关格式调整、调试残留）。*
5. **卡住** — 同一问题三次失败就停，换假设而不是换措辞。求助时给三样：试过什么、观察到什么、当前假设。验证路径本身怎么设计不在这里，走 verification-planning。

## 工程准则（启发式：默认遵循，有更好理由可偏离并说明）

- **恰到好处** — 只实现被要求的功能，不写"未来可能用到"的扩展点。单一实现不需要抽象；同样的逻辑出现第三次才是抽象的时机。没有测量数据的性能优化不做。
- **结构纪律** — 编辑优先于新建，新代码默认放进职责相近的既有文件。拆分的理由是"职责混杂"，不是行数：内聚的 500 行好于 5 个破碎的 100 行。判定细则见 `references/code-organization.md`。
- **复用有门槛** — 已有函数能覆盖大部分需求时，扩展它或提取共享部分。提取的标准是**领域无关性**，不是被 import 的次数：common/utils 里出现业务词汇即是违规信号。长得像的两段代码，只有当它们承载同一份知识、必然同步变化时才合并。
- **外科手术** — 只改任务要求改的部分。顺手改善的边界是你本来就要触碰的那几行；更大的改进冲动写进汇报，不动手。遵循项目既有风格，即使你觉得它不好。清掉自己制造的垃圾（调试打印、注释掉的尝试、被改动废弃的旧代码）；与本任务无关的死代码报位置，不擅自删。

原则冲突或要偏离时，读 `references/principle-tradeoffs.md`。

## 完成汇报

四项，每项必填：

1. **改了什么** — 文件与要点；有新增／删除／移动文件就单列并附理由。
2. **怎么验证的** — 跑了什么、结果如何。
3. **没验证什么** — 明确写"无"，不要省。
4. **剩余风险与建议** — 已知边界、克制没做但值得做的事。
