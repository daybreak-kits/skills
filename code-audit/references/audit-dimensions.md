# 审计维度详解（按需加载）

本文件是 SKILL.md「七个维度（覆盖清单，不是打勾表）」一节的展开。以下维度是关注方向，不是逐条打勾的清单。依据代码实际风险分布灵活分配精力，不要在每个维度上均匀用力。**出现的具体数值均为经验参考起点**，需结合语言习惯和项目基线自行校准，不是逐条比对的硬性红线。

## 贯穿各维度：地基债与污染检查

地基债的判定标准在 SKILL.md「定级」一节（多真相 / 藏真相 / 无反馈）。它不是一个独立维度，而是在每个维度里都可能浮现的一种性质——下面各维度中标注"地基债信号"的地方，是该维度最常见的浮现形态，不是全部。

**污染检查**是对每条地基债候选都要做的一步，目的是回答"已经有谁建在它上面了"：

- 检索非权威候选的调用方与引用方（代码、测试、文档、脚本）
- 检查近期提交、测试结论、实验记录、分析报告中，是否有声称基于某参数/某实现得出的结论，而该参数实际被写死、该实现实际未在生产路径
- 有 → 列为受污染产物，定级升阻塞；无 → 保持主要

这一步通常只需几次检索，不要省略——它决定的是"这是债"还是"已经有错误结论在被当作事实使用"。

## 1. 调用链与数据流

**目标**：确保局部修复不会崩溃上下游，数据在整条链路上不会在边界处爆炸，决定行为的参数真实可控。

- 向上追溯调用方（传入什么、对返回值有什么假设）、向下追溯被调用方；函数签名变更时扫描所有调用方确认兼容性，不兼容的列入"联动修复项"
- 隐式依赖（全局变量、单例、Context / Store / Session）需明确列出
- 明确关键参数来源（用户输入 / 外部 API / 数据库 / 内部计算）；来自外部的数据未经校验直接使用 → 安全/健壮性缺陷；存在截断、覆盖、丢弃风险 → 标记并给出防御方案
- **决定行为的参数要追到真正生效处**：阈值、开关、环境标识、路径、超参等，沿链路追到它最终被读取的位置，确认中途没有被常量覆盖、被默认值吞掉、被另一份配置抢先。**地基债信号**：上层看似可配置而下层写死；多份配置源互相覆盖且优先级不显眼；同一参数在不同层有不同默认值
- 横切式变更（同一改动散布在多文件/多层）：显式列出跨文件的联动点，验证各处修改的语义一致；这是"局部都对、整体错位"的高发区
- 异常传播：验证调用栈上层是否有对应处理；整条链路无任何处理点 → 阻塞。系统内部逻辑用 try-catch 埋掉错误需标记——原则上仅允许在外部不可控边界（第三方库、网络/系统 IO、跨模块服务调用）使用异常捕获，不要用默认值/fallback 掩盖本应修复的问题

### 参数层缺陷（实参对位时对照）

**这一层的共同特征：代码跑得通、测试全绿、行为与意图相反。** 类型检查、lint、单测都不会报，因为每一行单独看都合法。

| # | 形态 | 机制 | 观察点 |
| --- | --- | --- | --- |
| 1 | **漏传** | 关键参数不传，库默认值与业务意图相反 | 调用点实参列表 vs 函数签名；库默认值是多少 |
| 2 | **默认值吞掉** | 深层的常量/默认值覆盖上层传入值 | 沿参数追到最终被读取处，看中途有无重新赋值 |
| 3 | **索引叠套** | 已是行序/元素级的数据又按编号索引一次 | 同一数组上是否出现第二个 `[...]`，块长是否可能 ≥2 |
| 4 | **掩码错位** | 长度不等的两数组用同一掩码/切片对齐 | 两个数组的 shape 或区间是否一致 |
| 5 | **单位/方向** | 百分比与小数、分与元、正负号、买卖方向反了 | 变量名带单位吗；比较符与业务方向一致吗 |
| 6 | **短路** | 参数传了，但下游分支根本不读取它 | 该参数是否真的进入了决策路径（shutdown 而非 read） |

真实案例（不同语言、不同领域，仅供校准“什么算命中”，不是要复现的形状）：

- **漏传**：Python 训练框架里建 study 时不传 direction，默认 MINIMIZE，而目标函数返回“越大越好”的指标 —— 搜索预算全部花在低分区，冠军仍在历史最优点，因此监控、日志、测试都没异常，只有“最优值随轮次下降”这一个信号。
- **索引叠套**：标签计算把“每个 spec 的时序参数”按 spec 数量 repeat 成行序，再拿 spec 编号索引一次；块长 ≥2 时所有行都取到第 0 个 spec 的值。单 spec 调用（长度 1）完全正确，所以测试与生产长期共存。

## 2. 代码逻辑与安全

**目标**：识别会导致运行时错误或安全漏洞的代码缺陷。

### 逻辑缺陷

- 空值处理、边界条件、未捕获的 Promise / 未处理的异常
- 写操作与外部 API 调用的幂等性保障（重试场景是否产生重复副作用）
- 涉及 IO / 全局状态修改 / 缓存失效的副作用边界
- 持久化状态变更缺乏日志或事件记录 → 可观测性缺陷

### 安全（对齐 OWASP 关注类别）

安全缺陷的一个本质困难：**缺失的控制看起来就像正常代码**——缺失的授权检查看起来像普通代码，字符串拼接的 SQL 看起来就是个查询，缺失的校验步骤"什么都看不到"。因此安全审计要主动查"应有而未有"，不能只看"写了什么"。

按下列类别系统性过一遍（不只查最熟悉的那两三类）：

- **访问控制（最高优先）**：越权访问、缺失的鉴权/授权检查、水平/垂直越权、不安全的直接对象引用（IDOR）。这是长期排名第一的风险类别，审查时间有限时优先查它
- **注入**：SQL 拼接、命令注入、危险函数（`eval` 等）、模板注入
- **加密失败**：弱算法（MD5/SHA-1/DES）、硬编码密钥、敏感数据未加密、非加密安全的随机数用于 token/salt/nonce
- **安全配置错误**（排名第二的风险）：不安全的默认值、开启了不必要的功能、调试接口暴露
- **认证与会话**：弱凭据处理、会话管理缺陷、token 熵不足
- **异常条件处理不当**：吞掉的异常、错误消息泄漏堆栈/内部路径/schema 提示、失败时降级到不安全状态
- **软件供应链**：新引入依赖是否携带已知 CVE、未签名更新、不安全的反序列化；**依赖版本基线**——依赖长期落后或锁定在特殊版本时，检查代码假设、文档与实际版本是否一致。**地基债信号**：代码按旧版 API 编写但清单中无版本约束说明；版本与当前主流用法已分叉而代码里看不出来——后续接触者会按自己熟悉的用法写，行为静默不同
- **SSRF / 数据完整性 / 日志与监控失败**：SSRF 入口、敏感数据落日志、鉴权事件无审计轨迹

发现密钥、密码、token、PII 等，按 SKILL.md「必须遵守」第 4 条（冲突不裁决）与第 1 条（只读）的纪律处理——只引用位置和类型，不回显明文。

**高风险路径强制**：变更涉及并发、支付、认证、公共接口、迁移脚本等高风险路径时，报告中必须包含对应的深度安全/并发评估，不得一笔带过。

## 3. 无效与冗余（维度 3 的执行层）

分类用于识别，**定级看误导性**：一个看起来完整可用的旧实现，比一个未使用的导入危险得多——前者会被后续接触者选中并在其上继续开发，后者只是噪音。同属"死代码"，前者是地基债（主要起），后者是次要。

**死代码**（永不执行）：不可达路径、永假分支、从未调用的函数、未使用的变量/导入。标记前须确认不是对外公开 API、不是框架反射/DI/事件系统调用的方法、不是副作用加载的导入。**地基债信号**：从未调用的函数看起来像一个完整可用的入口（有文档、有签名、名字合理），局部读者无法得知它不在生产路径上。

**冗余代码**（执行但无净效果）：立即被覆盖的赋值、空 catch 块（无日志无处理）、结果被丢弃的纯函数调用、永真条件守卫、多余类型转换。有明确注释说明"有意忽略"的空 catch 块不强制标记。**地基债信号**：被立即覆盖的赋值如果来自配置注入，意味着"看似可配置实际写死"——转到维度 1 处理。

**过时代码**（曾经有意义但依据已消失）：已固化的 Feature Flag、已修复 Bug 的 Workaround、废弃 API 调用、已执行但仍可重入的迁移脚本（若可产生破坏性副作用 → 阻塞）、长期无进展且无关联 issue 的 TODO/FIXME/HACK。**地基债信号**：废弃接口仍可被调用且无弃用标记，与现行接口并存——局部读者无法判断该用哪个。

**僵尸代码**（以"备用"形态残留的旧实现）：新旧实现并存且旧实现无调用方、长期 skip 且无关联 issue 的测试、大段注释代码块（Git 历史已保存，注释代码不提供额外价值）、ROADMAP 外的过度抽象（单实现接口且无扩展计划，测试 Mock 除外）。**地基债信号**：新旧实现并存几乎总是地基债；长期 skip 的测试让人以为该行为有保护，也是。注释代码块通常不是——它明显不在运行。

**全局信号词扫描**：完成逐函数审计后，对 `old`、`legacy`、`backup`、`deprecated`、`temp`、`unused`、`todo`、`v1`/`v2`、`_new`/`_old` 等命名做一次全局排查，作为补漏手段。

## 4. 重复代码

**目标**：识别值得合并的冗余，确认哪一份是权威，同时避免过度聚合。

**核心判断标准**：同一业务规则或算法结构在多处独立实现，且"规则变化时多处必须同步修改"→ 标记为重复。"结构相同"基于算法骨架（分支结构、循环逻辑、调用顺序），而非名称或注释相似。这与 DRY 原则的实质一致：需要抽离的是"知识/规则的重复"，不是"文本的相似"。

**重复代码必须回答"哪一份是权威"**：通过生产调用路径确认实际在用的是哪一份。重复的危害不只是"改一处漏一处"，更在于后续接触者选错一份——在非权威实现上继续开发，或者两份各自演化出不同行为。**地基债信号**：两份都看起来可用、只有一份在生产路径上、且局部无法分辨；或两份都在用但行为已悄悄分叉。这种情况下即便代码量不大也不适用"三次法则"的容忍——问题不在重复本身，在歧义。

**不视为需要合并**：短小低频的相似片段；框架样板代码；结构相似但业务概念独立、各自独立演化的"假孪生"；跨层职责不同的相似逻辑；测试中有意保留的 setup/teardown 重复；多个类实现同一接口产生的结构镜像。

**灰色地带**（报告中说明判断依据）：中等规模相似代码仅出现两处 → 标注"潜在重复，若两处经常同步修改则建议提取"；if/switch 分支判断同一类型字段 → 仅当类型频繁增加时才建议引入策略模式。（"三次法则"可作参考：出现两次可容忍，第三次再抽离，避免过早抽象带来的错误耦合。）

## 5. 设计质量与架构

**目标**：识别需要结构性改善的代码和影响系统可持续性的架构风险。以下经典设计原则作为判断透镜（是启发不是打勾项）：SRP（单一职责——描述一个模块要用"和"字往往意味职责失控）、OCP（对扩展开放对修改封闭）、SoC（关注点分离，层间依赖方向正确）、KISS/YAGNI（避免过度工程与投机性实现）。

重构信号（满足任一即输出重构建议）：圈复杂度明显偏高或单函数明显过长（参考起点：>10 / >80 行，按语言基线调整）；多处 if/switch 判断同一类型字段且该类型频繁扩展；模块间存在双向依赖；结构导致难以测试（深层耦合、无接口抽象）。

架构风险信号：循环依赖或层级越权调用；变更核心逻辑但缺乏日志/监控埋点；修改公共函数/共享类型/全局配置时列出影响范围；需要策略模式或插件化的场景中使用了硬编码判断。

**权威位置缺失**（地基债信号）：同类事物——配置、测试、脚本、文档、常量——没有一个单一的、可发现的所在，而是散落在多处。后果不是"乱"，而是后续接触者找不到已有的，于是重新造一份，或者以为不存在于是跳过。判断时看"一个合理的接触者会不会找得到"，而不是看是否符合某种目录规范。

重构建议必须包含：当前问题 → 建议方案 → 对调用方的影响评估。注意区分：重构进入独立清单，不与阻塞性修复混淆。

## 6. 需求覆盖

- **代码 → 需求**：实现是否符合 spec 描述（数值、行为、边界）
- **需求 → 代码**：spec 中每一条要求是否都有对应实现，未实现标记为 GAP
- **额外功能**：需求文档中不存在的额外实现 → 标记为"镀金功能"，评估其引入的技术债务

对影响行为、安全、资金的变更，若 spec 缺失明确验收标准，应在"待确认项"提出需要先对齐的具体验收断言（例如"页码超过 100 应返回 400"这类可判定的标准），而不是凭代码反推"大概是对的"。

## 7. 测试可验证性

- 每条阻塞/主要缺陷修复建议同时提供可验证的测试断言（输入 X → 预期输出 Y → 不应触发 Z）
- 核心路径无对应测试的函数 → "补充测试覆盖"列为联动修复项
- 被 skip 的测试 + 未使用的测试 helper + mock 了不存在的函数 → 综合评估实际有效覆盖率
- **测试不能自证**：现有测试（尤其是与被测代码可能出自同一误解、或由生成工具产出的测试）通过，不构成"实现符合需求"的证据。当测试断言本身就固化了错误行为时，要指出"测试锁定了错误预期"，而不是把绿灯当正确
- **声称的覆盖 vs 实际生效的覆盖**：当测试、实验或分析声称覆盖了多个参数取值、多个分支、多种环境时，追溯被变化的那个量是否真的沿链路生效（见维度 1 的参数追溯）。参数在入口被改了、却在下游被写死覆盖，那么"测了 1/3/5"实际上只测了一个值——结论的广度是假的。这类发现几乎总是地基债并且污染已经发生（结论已经产出），按阻塞处理并列出需作废重跑的产物
- **测试的可发现性**：同一被测对象的测试散落在多个不相关位置，或测试文件命名/位置与被测代码无法对应时，后续接触者会以为没有测试而重写、或以为已有覆盖而跳过。按维度 5 的"权威位置缺失"判定
